# Skill: migration

## Passo 1 — descubra o próximo número (não adivinhe)

```bash
ls src/main/resources/db.migrations/
```

A pasta é **`src/main/resources/db.migrations/`** — com **ponto**, não barra. Isso vem de `spring.flyway.locations: classpath:db.migrations` no `application.yaml`. Criar em `db/migration` faz a migration ser silenciosamente ignorada.

Nome: `V<n>__snake_case_descricao.sql`, sem zero à esquerda.

## Passo 2 — escreva

Siga o estilo das existentes:

```sql
-- Uma linha dizendo o porquê da mudança.

CREATE TABLE exemplos
(
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id   BIGINT       NOT NULL,
    nome      VARCHAR(120) NOT NULL,
    criado_em TIMESTAMP    NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_exemplos_user_id FOREIGN KEY (user_id) REFERENCES users (id),
    CONSTRAINT uq_exemplos_user_nome UNIQUE (user_id, nome)
);

CREATE INDEX idx_exemplos_user_id ON exemplos (user_id);
```

Convenções do projeto: `fk_<tabela>_<coluna>`, `uq_<tabela>_<colunas>`, `check_<tabela>_<regra>`, `idx_<tabela>_<colunas>`.

## Regras

- **Sintaxe só PostgreSQL.** O perfil de teste não roda Flyway (gera o schema das entidades), então erro de sintaxe **não aparece em teste** — aparece em produção.
- **Nunca edite uma migration já aplicada.** O Flyway valida checksum e o boot falha. Corrija com uma migration nova.
- Toda regra que um validator garante deveria ter espelho no banco (`UNIQUE`, `CHECK`). Validação só na aplicação é contornável por corrida.
- Coluna nova `NOT NULL` em tabela com dado precisa de `DEFAULT`, ou de `UPDATE` antes do `SET NOT NULL`.
- FK sem índice na coluna filha deixa o `JOIN` lento. Crie o índice.

## Passo 3 — sincronize o resto

1. A **entidade JPA** precisa refletir a coluna: `@Column(name = "...")`, e enum **sempre** com `@Enumerated(EnumType.STRING)`.
2. Se o campo é obrigatório, confira se os **helpers de teste** (`RepositoryTestBase`, `TestData`) precisam preenchê-lo — senão os testes quebram com violação de `NOT NULL`.
3. Não existe dump do schema para manter. O `db/soulie-schema.sql` foi removido na Fase 2: ele prometia "schema final" e estava 8 migrations atrasado, então quem o executasse ganhava um banco quebrado. O schema é o que as migrations produzem, e nada mais.

## Passo 4 — verifique

`./mvnw -q clean verify` cobre a parte das entidades. A migration em si só é exercitada contra um PostgreSQL de verdade — se houver um disponível, rode a aplicação e confirme que o Flyway aplicou.
